# Spec-driven workflow

`openspec/specs/` is the **source of truth**; code implements it. When spec and code disagree,
decide which is wrong and fix it on purpose: a wrong spec through a change, code that breaks a
correct spec as a bug fix. Read `openspec/conventions.md` before writing or changing a spec.

## The flow of one change

0. **Start clean.** If `openspec/changes/` holds an active change (any folder but `archive/`),
   run `/sdd:archive-pr` first: an archive-only PR, merged once it is shown to be mechanical.
   Then branch the new work from the updated default branch.
1. **Propose** with `/opsx:propose`: proposal, spec deltas, design (its open questions and the
   assumptions the change proceeds on), tasks. A delta that creates a new capability starts with
   `## Purpose` of at least 50 characters, or its archived spec fails strict validation.
2. **Check** with `bash scripts/sdd/check-specs.sh` after committing the change: the specs must
   validate both now and once the change is archived.
3. **Spec review** with `/sdd:spec-review <change>`. It runs as a fresh agent, before any code.
   Fix findings through the spec (`/sdd:spec-fix`) and review again only while the last round
   found a blocker. At most 3 rounds per change unless the owner says otherwise.
4. **Apply** with `/opsx:apply`: tests from the new or changed scenarios first, seen to fail,
   then the code.
5. **Conformance review** with `/sdd:conformance-review <change>`: does the code do what the
   spec says, and nothing the spec doesn't? Route its findings with `/sdd:spec-fix`.
6. **Open the PR.** One PR carries the change's spec and its code. Never archive in it.

A copy-only change (wording, typos, links; no requirement's meaning changes) may skip step 3;
its proposal says so.

## Rules

- **Fixes go through the spec.** A review finding, UAT remark or bug that changes what the
  software does is a spec change first: delta, check, commit; then the failing test; then the
  code. Never change code and back-fill the delta in the same commit. `/sdd:spec-fix` does this.
- **Nothing the owner hasn't decided goes in as a requirement unmarked.** It is an open
  question in `design.md`, with the assumption the change proceeds on.
- **Never archive inside a change's own PR.** Archive after merge, in its own PR.
- **Run OpenSpec as `bash scripts/sdd/openspec.sh <args>`** (pinned, telemetry off), never as
  `npx openspec`. OpenSpec's own skills (`openspec-*`, `/opsx:*`) are generated by
  `npm install`, gitignored, and never edited. Don't name your own skills `openspec-…`.
- **Read check verdicts from the job log.** The `sdd-checks` job prints one line per check,
  `<check>: <state>`; agents can't read commit statuses, so read the log through the Actions API.
- **CI checks a PR with the default branch's tools.** `sdd-checks` runs the scripts and the
  pinned OpenSpec CLI from the default branch, and reads the PR only as data. A PR that changes
  `scripts/sdd/`, `.github/workflows/` or the OpenSpec pin in `package.json` is checked with the
  old ones until it merges, so run `bash scripts/sdd/check-specs.sh` locally on such a PR.
- **The conformance review is the code review.** Every change gets `/sdd:conformance-review`,
  not a general code review: the spec was already reviewed for intent, so the code is checked
  against it.
